## 一、最终目标

开发一个独立运行的售前招标解析任务监测与诊断系统：自动发现任务异常，采集必要证据，给出可追溯的原因判断或明确的不确定说明，提醒负责人，并支持人工关闭及恢复跟踪。

负责人无需持续查数据库、登录服务器翻日志，也无需先输入任务 ID。打开管理页面即可回答：哪个任务异常、异常持续多久、有什么证据、可能是什么原因、需要谁做什么、是否已经处理。

首期交付为本机 Docker 可运行的业务闭环。监测、事件、取证编排、诊断、通知和管理 API 的主体使用 Go；前端使用 TypeScript。Akmatori 是技术栈、工程组织和实现方式的参考，不是基础平台或运行依赖。

## 二、业务对象与功能范围

只监测 handoff-20260831 契约下的 bidding 异步解析任务。使用独立模拟业务服务、MySQL 和合成日志验证，不运行或修改公司业务系统，不接真实业务数据库。

| 业务情况 | 系统行为 | 判断边界 |
| --- | --- | --- |
| 任务明确失败 | 建立异常事件、取证、提醒 | 失败状态不能直接说明失败原因 |
| pending 超过阈值 | 连续确认后提醒排队异常 | 不直接断言 Worker 已宕机 |
| running 长时间没有有效进展 | 建立运行停滞候选并检查证据 | 时间戳变化不必然代表业务进展 |
| completed 后没有结果 | 经过落库宽限及复查后提醒 | 允许任务状态与结果分事务提交 |
| 结果存在但所有目标提取项为空 | 建立空结果复核候选 | 不认定原文为空，不直接判为失败 |
| JSON 损坏、结构错误或重复结果 | 标记结果结构/关联异常 | 不转换成“空结果” |
| 业务数据源暂时不可用 | 展示监测故障，保留既有事件 | 不把采集失败当成任务恢复 |

识别明确日志错误时，可给出额度不足、限流、模型请求超时、提取失败等分类；不支持的供应商错误或证据冲突保留不确定。诊断仅使用实际取得的状态和日志，不读取模拟器的场景答案。

人工关闭必须填写原因，例如“这是实验故意制造的失败，不需要继续处理”。关闭状态为 closed_unresolved，不代表恢复；停止该事件后续诊断和提醒，迟到结果只归档。同一异常持续存在时不重新报警，确认解除后再次发生才建立新一轮事件。自动恢复与人工关闭分开记录。

## 三、技术栈与借鉴方式

下表的“上游事实”来自本地 Akmatori 源码核查：Go 模块、HTTP 启动代码、前端 package.json 及已有组件核查。具体依赖版本在实施时锁定，不将“上游使用的版本”误称为最新版本。

| 层次 | 本项目计划 | 与 Akmatori 的关系 |
| --- | --- | --- |
| 后端语言与 HTTP | Go、标准库 net/http、context、结构化日志 slog | 沿用其 Go 后端、标准 HTTP 服务的技术方向，独立 Go module 和入口 |
| 工程组织 | cmd、internal 下分 handler/service/repository/adapter | 借鉴其分层与接口组织，按售前业务裁剪 |
| 监测库 | PostgreSQL、GORM；版本化 SQL 迁移 | 上游采用 PostgreSQL/GORM；本项目单独设计事件、证据、作业、Outbox 表，不搬整套数据库 |
| 业务库访问 | MySQL 只读账号，database/sql 与 MySQL 驱动 | 售前业务专用适配；采用显式查询处理增量游标和结果关联 |
| 后台执行 | goroutine、ticker、context、有限 worker pool，数据库保存游标及作业 | 借鉴并发服务组织；持久化、超时和重试边界由本项目实现，任务扫描不必引入 cron |
| SSH 取证 | Go 的 golang.org/x/crypto/ssh、固定主机密钥、目标端 forced-command Helper | 借鉴工具抽象和远程取证方式；Go SSH 实现为本项目选择，不声称直接照搬上游 SSH 内部实现 |
| 诊断 | Go 规则分类器、结构化报告校验、可选模型适配接口 | 借鉴工具结果组织、运行手册、证据引用和执行预算；不引入完整通用 Agent |
| 管理页面 | React、TypeScript、Vite、Tailwind CSS | 与上游前端技术方向一致，仅实现业务必需页面，不复制整套控制台 |
| 通知 | Go HTTP 客户端、PostgreSQL 事务 Outbox、通知适配接口 | 借鉴消息渠道抽象；本地接收器首期可用，飞书后续接入 |
| 部署 | Docker Compose；前端构建产物由 Go 服务提供 | 借鉴容器化部署，独立名称、网络与卷；不要求单独部署 Nginx |
| 验证 | Go testing/httptest、真实数据库集成测试、页面及端到端验收 | 复用已有业务验收场景；原 Python 测试通过不等于 Go 已通过 |

不引入 Redis、Kafka、Kubernetes 或独立任务队列服务。单个 Go 服务内分开运行扫描、诊断和通知循环；首期不做多副本调度平台。

管理页面本机访问且需要身份认证；凭据不打包进前端。优先采用简单的单用户会话与写操作保护，不扩展为多租户权限系统。

## 四、具体借鉴和独立实现边界

### 借鉴 Akmatori

1. 告警规范化：统一事件字段，而不是让每种业务故障各自维护一套消息格式。
2. 稳定指纹与去重：参考指纹计算方式，按本项目的来源、环境、任务、规则和 episode 定义身份。
3. 事件生命周期：参考事件、报告、状态及审计的组织，但“业务恢复”仍由业务观察确认。
4. 工具与适配器接口：把业务读取、证据采集、诊断和通知分开，便于替换与测试。
5. 执行预算：诊断设总时限、并发上限和工具调用上限；失败不能堵塞扫描和初始提醒。
6. 前后端工程方式：借鉴 Go 服务分层、GORM 存储、React 页面组织和 Compose 部署。

### 本项目独立实现

- 售前任务及结果的数据契约、增量扫描、活动任务复查和异常规则。
- 业务事件状态机、空结果候选判断、人工关闭抑制与恢复判断。
- 受限取证、脱敏、售前场景诊断规则及证据校验。
- 事件中心、详情页、通知投递和操作记录。

直接复制代码只限经过审查、确有价值且依赖合理的小组件，记录固定提交、路径、许可证和修改说明；不为方便复制而引入整套依赖。不复制 Akmatori 数据目录、凭据或未审查的本地修改，不修改参考项目。

最终只有 bid_mon 自己的一套业务事件和报告，不向另一套 Akmatori incident 转发，不维护重复绑定关系。通用告警 webhook、通用 Agent、MCP Gateway、Slack、跨事件智能合并均不是本期必做能力。

## 五、用户最终能使用的页面

1. 事件中心：查看待处理、已恢复、人工关闭的异常；按任务、异常类型、状态筛选，看到最后更新时间。
2. 事件详情：任务状态、触发规则、时间线、诊断结论、证据、处理建议、通知状态；填写原因关闭。
3. 运行状态与本地通知：展示最近成功扫描、数据源/取证故障、诊断或投递失败，以及实际收到的本地通知。

页面显示“规则诊断”“证据不足”“本地通知”等真实状态。没有模型渠道时，不展示模拟报告来制造 AI 已完成诊断的效果；模拟模型适配器只用于故障测试。

## 六、实施顺序与每阶段验收

| 阶段 | 开发内容 | 阶段完成条件 |
| --- | --- | --- |
| 1. 统一基线与 Go 骨架 | 更新目标文档；独立 Go module、配置、HTTP、数据库、迁移和健康接口；冻结必要 API 契约 | Go 服务可在 Docker 独立启动；确定与旧实验数据兼容的迁移方案；没有 Akmatori 运行依赖 |
| 2. 自动监测与事件 | 迁移扫描、结果检查、确认计数、游标及状态机；实现事务 Outbox 和本地通知 | 自动发现 failed 任务并收到一条逻辑初始提醒；宽限内及正常任务不误报；重启、关闭、恢复可验证 |
| 3. 取证与业务诊断 | Go SSH 客户端与受限 Helper；脱敏、规则分类、报告校验、预算及持久化作业 | 从合成业务日志取得证据并正确分类；证据缺失、超时、注入文本和伪造引用不产生错误确认结论 |
| 4. 人工操作页面 | React 事件中心、详情、关闭、运行状态和本地通知 | 可通过页面完成“发现问题—看证据—填写原因关闭”，无需使用 API 文档处理日常事件 |
| 5. 整体验收与切换 | 全场景回归、通知故障与服务重启检查、启动文档、旧路径退役 | Docker 一键启动最终 Go 系统；核心运行不依赖 Python 监测器或 Akmatori 服务；验收记录与实际结果一致 |

阶段 2 先完成最短业务闭环，再扩展诊断和页面。每阶段都提供可运行结果及剩余限制，不用“搭建了框架”代替业务验收。

## 七、现有实现如何处理

- 保留既有业务规则、接口契约、合成数据、场景和测试思路，作为 Go 实现的参考与回归基线。
- Python 监测核心逐步替换，Go 版本验证通过后切换；同一来源同一时刻只允许一个主动监测器，避免双重通知。
- 过渡期允许保留 Python 模拟器和验收脚本；它们不是最终监测系统的运行核心。目标端取证 Helper 纳入 Go 迁移，尽量保留已验证的协议和限制。
- PostgreSQL 迁移需明确表兼容性、事件身份及回退步骤。已有事件、关闭原因和证据不直接清空；必要时保留只读历史，禁止暗中丢弃数据。
- 已加入的 Akmatori 接入服务、独立数据库服务及重复 incident 绑定退出最终 Compose；替代路径验收通过后停用。历史卷、源码出处和验证记录保留，不直接删除实验数据。
- 切换须先通过数据库与业务回归，停用旧主动监测器后启动 Go；当前本机已按此步骤切换，历史服务与卷保留用于回退。

## 八、最终验收标准

1. 模拟服务新增任务后，系统自动发现；无需人工登记任务 ID。
2. 所列异常场景有对应判断；正常、取消、部分提取项为空、宽限内结果延迟不被误判为整体失败。
3. 结论能够指向实际证据；证据不足保持不确定，错误 JSON 或重复结果不被当成空结果。
4. 在无积压、依赖正常的单任务验收下，failed 任务在一个扫描周期加处理余量内建事件，目标不超过 30 秒；需连续确认的规则按阈值、宽限和确认次数计算，不承诺立即触发。
5. 诊断默认总预算 120 秒，超时记录可见；不因诊断失败丢失初始提醒。队列等待计入诊断预算。
6. 重启保留游标、事件及关闭状态；重复扫描、重复响应和重试不创建重复逻辑事件，不承诺网络严格一次送达。
7. 人工关闭原因必填，同一持续异常不重新提醒；迟到报告不追加诊断通知；真正解除后再次发生建立新 episode。
8. 业务数据库只读、SSH 命令受限、证据脱敏；不自动重跑任务、修改业务数据或重启业务服务。
9. 管理页面能够实际完成查看、追溯与关闭；采集/通知失败可见且有有限重试，不伪装成功。
10. 最终核心使用 Go，独立 Docker 运行，不要求启动 Akmatori，不包含无业务价值的重复事件和模拟报告层。

## 九、首期交付物与后续条件

交付：Go 后端、业务管理页面、Compose、模拟业务与日志环境、数据库迁移、自动化验收、启动及操作说明、Akmatori 借鉴清单。

没有真实模型和飞书渠道不阻塞首期本地交付；预留适配接口，但真实模型诊断效果及飞书送达必须在渠道可用后单独验收。生产业务接入、文档语义质量审查、多租户、通用运维平台和自动修复不属于本期目标。
