# 售前任务自动监测与 AI 辅助诊断系统（bid_mon）

## 简历正文

**业务背景：** 面向售前招标文件解析场景，异步任务可能出现执行失败、排队超时、运行停滞及结果缺失等问题，通常需要人工查询数据库、登录服务器排查日志，异常发现和原因定位过程分散。开发独立的任务监测与诊断系统，形成“异常发现—证据采集—原因分析—通知—人工关闭—恢复跟踪”的处理闭环。

**技术栈：** Go、net/http、Goroutine/Context、GORM、PostgreSQL、MySQL、SSH、OpenAI Responses 兼容模型接口、React、TypeScript、Vite、Tailwind CSS、Docker Compose；使用 Python/FastAPI 构建模拟业务与本地通知服务，使用 Go 竞态检测和 Playwright 完成验证。

**主要工作：**

1. **独立系统设计与交付：** 借鉴 Akmatori 的 Go/GORM/PostgreSQL 技术栈和诊断上下文组织方式，按售前业务裁剪能力，独立实现 Go 后端、管理页面与 Docker 部署，避免依赖上游整套平台。
2. **异常监测与事件管理：** 基于只读 MySQL 访问实现增量游标扫描、重叠窗口、活动任务复查及周期校对，覆盖失败、排队超时、运行停滞、结果缺失与结构异常；通过连续观察降低误报，将“全部目标提取项为空”定义为人工复核候选。
3. **事件生命周期与可靠通知：** 设计事件指纹、异常轮次及状态流转，区分业务恢复与人工关闭，支持持续异常去重、恢复后复发及关闭原因审计；使用 PostgreSQL 事务 Outbox、有限重试和投递状态记录，保证诊断失败时仍能发出初始异常提醒。
4. **受限取证与 AI 辅助诊断：** 使用 Go SSH 客户端与固定 Helper 采集任务日志、模型错误及 Worker 心跳，落实主机密钥校验、签名绑定、采集范围限制和脱敏；接入真实模型补充分析与处理建议，校验结构化输出及证据引用，并以并发限制、总时限和规则回退控制失败影响。
5. **可视化处理与验收：** 开发事件列表、诊断详情、证据编号对照、通知状态及人工关闭页面；完成数据库、SSH、故障恢复与浏览器验收，并隔离测试 MySQL，避免集成测试数据触发主监测器的模型调用。

**项目结果：** 在本机 Docker 完成模拟业务与真实诊断模型的闭环验证：79 个 Go 测试通过项（含子测试，竞态检测通过）、28 项业务回归、11 项浏览器检查；约 6 分钟持续投放 36 个合成任务，异常最大发现耗时 15.148 秒，本轮正常/取消任务无误报、异常事件无重复。

## 篇幅有限时使用的精简版

**售前任务自动监测与 AI 辅助诊断系统｜Go / PostgreSQL / MySQL / React / Docker**

- 面向售前招标解析异步任务，独立实现异常监测、受限日志取证、AI 辅助诊断、通知及人工关闭的业务闭环。
- 通过增量扫描、连续观察、事件指纹与异常轮次识别失败、排队停滞及结果异常；基于事务 Outbox 实现初始提醒与诊断更新，支持去重、有限重试和状态追溯。
- 使用 Go SSH Helper 约束取证范围，结合证据脱敏、引用校验、诊断预算及规则回退，接入真实模型生成可追溯的分析和处理建议。
- 交付 React 管理页面和本机 Docker 环境，通过 Go、业务故障及浏览器验证；36 个合成任务的实验中，异常最大发现耗时 15.148 秒。

## 面试说明与数据口径

- **定位：** 这是独立开发的业务系统，不是 Akmatori 二次开发，也没有实现通用 Agent/MCP 运维平台。
- **落地范围：** 已在本机 Docker 运行；业务数据、任务日志及 Worker 使用模拟服务，诊断模型真实接入。真实客户业务和群机器人尚未接入，不应写成已在企业生产环境上线。
- **AI 边界：** 模型补充证据分析与建议，不自主执行命令、不自动重跑或修复，不改变规则分类、确定性及业务恢复状态。模型内容仍需人工核对。
- **真实限制：** 持续投放期间 12 次模型调用中 9 次完成分析、3 次超时后回退规则报告；监测与通知仍完成。不能把规则回退计作模型成功。
- **指标含义：** 15.148 秒是本轮实验样本的最大发现耗时，不是生产 SLA；6 分钟验证不代表长期稳定性或高并发压测。未测量排障效率提升百分比、客户规模或业务收益，不建议编造这些指标。
- **材料依据：** 设计目标见 go-independent-plan.md，技术借鉴见 akmatori-reference.md，验收依据见 go-validation.md 与 artifacts 中的原始记录。
