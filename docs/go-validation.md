# 独立 Go 交付与验证记录

日期：2026-09-28。用户确认的独立开发路线见 go-independent-plan.md。本记录区分实际完成的实验功能、验证方式与未完成的外部接入。

## 交付结果

已实现并在本机 Docker 切换到独立 Go 监测核心。根模块 bidmon，Go 标准 HTTP 服务、GORM/PostgreSQL、database/sql/MySQL、Go SSH 客户端与 Helper；React/TypeScript/Vite/Tailwind 管理页面嵌入 Go 二进制。

五个计划阶段的实现均已落地：Go 工程与版本化 SQL、自动监测及事件通知、受限取证与规则诊断、人工操作页面、业务验收及本机切换。

当前 Compose 不包含 Akmatori 接入服务、数据库、Agent 或 MCP。旧 Python 监测器已被替换；旧 Akmatori 实验容器已停止，独立卷及既有关联表保留为历史。

## 业务流程

- 自动读取 bidding 任务，按增量游标、重叠窗口、活动任务复查和滚动校对发现异常。
- failed 立即建事件；排队、停滞、缺失结果、空结果候选和结果结构异常按规则确认。只有结构可识别、全部目标为空才触发空结果候选。
- 异常与初始通知同事务保存，规则诊断独立执行。诊断有队列/运行状态、总时限、并发上限和持久化证据。
- Go SSH Helper 从固定路径读取合成日志和心跳，返回脱敏证据；模型错误分类仅识别合成供应商明确错误码，不读取场景名称作为答案。
- 管理页面提供登录、事件筛选、结论与证据、关闭原因、处理时间线、本地通知与运行状态。
- 人工关闭保留原因，不代表恢复，持续异常不重复建事件。真正解除后再次发生建立新 episode；迟到报告仅归档，不追加诊断通知。

## 数据兼容与切换

沿用原 monitor_events、task_snapshots、diagnosis_jobs、delivery_outbox、event_audit、monitor_cursors 表。SQL 迁移为可重复执行的建表/索引补充及迁移版本登记，未执行 DROP、TRUNCATE 或删除历史数据。

Go 指纹兼容既有 Python 的 JSON 编码与 SHA-256 规则，并由固定样例测试覆盖。沿用 PostgreSQL 会话锁，防止两套主动监测器同时运行。先停旧 monitor/akmatori-intake/akmatori-postgres，再启动 Go monitor 与 Go ssh-target。

端到端验收抽查了此前 Akmatori 实验中已人工关闭的事件：原 event_id、关闭原因和原本地诊断报告仍可查询。此项是历史样本检查，不宣称对每一条历史记录做过逐字段比较。

原 SSH 身份和主机密钥保留，只切换 forced-command Helper。新签名请求使用 Go 协议，客户端和目标端一起升级；不能混用旧 Python 客户端与 Go Helper。回退步骤见 README。

## 权限与运行限制

- MySQL 账号只读；监测库可写。SSH 主机密钥固定，远端只运行固定 Helper，不开放 Shell 或端口转发；证据请求绑定任务、事件、操作、时间窗口、数量及短期签名。
- 管理 API 要求凭据，浏览器会话为 HttpOnly/SameSite Cookie，写操作核对来源及自定义头。接口仅发布本机端口。
- 通知超预算为 needs_attention；诊断超时和证据缺失在页面可见。服务退出依赖 Docker 重启，不提供外部独立心跳告警。
- 初次扫描与校对窗口默认近 24 小时，首次额外登记全部活动任务；不承诺覆盖业务库全部历史保留期。单实例、实验规模，未进行生产负载或长时间稳定性验收。
- 文本脱敏采用结构键和规则匹配，不能保证识别任意未标注客户姓名；当前只使用合成数据，不可据此直接开放生产日志。
- Go/Node/数据库基础镜像按摘要固定；OpenSSH apt 仓库未做快照锁定。

## 2026-09-28 真实模型与收尾更新

用户明确授权复用 Akmatori 的活跃中转站配置，并允许将本项目合成任务的脱敏证据发送至该中转站。本机已启用独立 Go Responses 客户端，模型为 gpt-5.6-sol；密钥保存在被忽略的本地配置文件，未复制到源码、镜像或报告。

补齐各类异常的具体检查建议。真实模型补充证据分析和人工建议，引用经过校验；规则类别、确定性和业务恢复状态保持由本地逻辑控制。模型调用超时或返回无效内容时，报告明确显示规则回退。

最终版本 Go 集成与竞态检测为 **25 个测试组、79 个通过项、0 跳过**，已在专用 test-mysql 中重新验证；测试不再向主监测器使用的业务 MySQL 写入种子任务，也不会因此触发额外付费模型请求。完整记录见 artifacts/go-tests.json。前端类型检查、生产构建及构建内 Go 单元测试通过。

实测发现并记录了三类边界：首次模型证据编号引用未通过校验；大量集成测试任务同时进入主监测器导致部分诊断超过队列预算；中转站连续请求存在单次超过 60 秒的情况。已改用短编号映射解决引用易错问题，并验证规则回退与初始通知不受模型失败影响。额度不足、日志注入场景实际模型分析成功；提取失败场景单独复测成功，建事件 14.172 秒，完整报告 28.219 秒。不能将三种场景分别成功说成所有连续请求均成功。

新增验收的定义和复现命令见 [模型与收尾说明](model-and-acceptance.md)。混合负载失败记录保存在 artifacts/go-model-acceptance-mixed-load.json，中转站超时记录保存在 artifacts/go-model-acceptance-upstream-timeout.json；当前批次及单场景结果分别在 go-model-acceptance.json、go-model-extraction_failed-acceptance.json，保留其真实通过/失败状态。

持续投放验收：**364.339 秒、36 个任务（12 异常、24 正常/取消）、最大发现耗时 15.148 秒**。12 个异常均有唯一事件及完成的诊断与通知；正常/取消任务无误报，结束时诊断队列清空、数据源连续失败数为 0。模型结果为 **9 次真实分析完成、3 次 model_timeout 后规则回退**，未把回退算作模型成功。额度、限流、请求超时及提取失败四类均有真实模型成功样本，引用均重新核验，业务恢复状态未被模型改写。记录见 artifacts/go-soak-acceptance.json、go-soak-model-details.json。

本次资源采样：Go monitor 内存约 **10.32–14.74 MiB**，结束时 **12.04 MiB**，重启计数始终为 0，进程/线程计数 16–17；CPU 采样 0.34%–53.08%。这只是约 6 分钟的实验规模观察，不能据此宣称生产压测或长期无内存泄漏。中转站响应波动是当前实际限制，系统已验证超时回退；未承诺每个事件都能在预算内得到 AI 分析。
