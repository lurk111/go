# 订单回调示例

这里的业务状态是 `WAITING_ACK / DELIVERED / DEAD_LETTER / CANCELED`，规则直接配置业务字段；通用引擎无需把订单伪装成招标解析任务。

选择 `monitor.mysql.yaml` 或 `monitor.postgres.yaml`，把 `ORDER_DATABASE_DSN` 指向业务库的**只读账号**。示例没有任何真实凭据。MySQL DSN 应启用 `parseTime=true&loc=UTC`；数据库时间应使用 UTC。示例 schema 供实验建表，监控程序不执行它，也不修改业务库。正式业务可以改查询别名和字段映射，复用原有表。

`fields` 类型支持 `string / int / double / bool / timestamp / json`。`identity` 使用映射字段，必须稳定且非空；聚合分组要显式指定分组字段作为 identity，单行全局聚合可省略 identity。相同查询中的重复 identity 会使整批失败。字段缺失或类型错误产生不确定观察，禁止把它解释为恢复。查询零行或原对象消失也不会自动恢复。

规则使用 CEL，变量有 `fields`、`previous`、`now`、`entity_key`。触发与恢复各自使用显式表达式，并分别连续确认。`CANCELED` 在本例两种表达式都不满足，表示未知，不冒充回调成功。`allow_model` 默认 false，示例无需模型也不产生费用；接入真实业务后必须另行决定是否允许把脱敏证据发送到配置的模型渠道。

SQL 首期仅支持单条 `SELECT`，不支持 CTE、末尾分号、写入、锁定、输出文件、已知阻塞/副作用函数、可执行注释及反斜杠转义字面量。值应使用 sqlx 命名参数；扫描参数为 `:window_start / :window_end / :after`，详情查询可用 `:entity_key` 和每个映射字段，例如 `:id`。以完整查询成功结果作为一批，不宣称仅凭示例 window 条件就具有增量游标语义。

查询在只读事务和时间、行数、返回数据字节预算内运行；超预算、连接中断或提交失败不会应用任何部分结果。限制只是保护措施，不能代替数据库只读权限、适当索引和成本审查。SQL 驱动可能先接收一条过大的单行字段再触发字节检查，因此查询自身也应截断大文本/JSON，避免扫描无界结果。扫描可读字段应限制在需要的业务状态和指标，通知与诊断还需要引擎的脱敏处理。

超时通过 Go context 和数据库驱动执行。特别是 MySQL，客户端取消后不保证服务端已经终止所有工作；正式只读账号和数据库应另设服务端查询限额、连接限额，先审查查询执行计划。SQL 字词过滤只提供额外防护，无法证明任何用户定义函数都没有副作用。PostgreSQL 和 MySQL SQL/日期计算有差异，示例分开提供，不把一条 SQL 宣称为跨数据库可执行。
